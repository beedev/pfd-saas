# Changes — 2026-09-09

## fix(amfi): NAVAll.txt went 6 columns → 8; parser silently dropped every fund

**Area:** `src/lib/services/amfi.ts`, `src/app/api/cron/tick/route.ts`,
`scripts/check-amfi-nav-feed.mjs` (new)

### What broke

AMFI changed the layout of `NAVAll.txt`, splitting the scheme name into three
fields (`Scheme Name` / `Plan` / `Option`), taking the row from 6 columns to 8:

```
118989;INF179K01XQ0;-;HDFC Mid Cap Fund;Direct Plan;Growth Option;233.745;08-Sep-2026
  [0]      [1]      [2]      [3]           [4]           [5]        [6]      [7]
```

`parseNavAll()` read the NAV from a fixed front offset, `cols[4]`. That offset
now lands on `"Direct Plan"`. `parseFloat("Direct Plan")` is `NaN`, the
`!Number.isFinite(nav)` guard fired, and **every data line in the file hit
`continue`**. The existing `cols.length < 6` guard did not catch it either —
8 ≥ 6, so the new format passed the length check and was then mis-read.

Verified against the live feed: the shipped parser returned **0 funds** from a
1.5 MB file.

### Impact

Total outage of the AMFI-backed surface, on prod (`vaspar-pfd` :9999), from
somewhere between 2026-08-16 and 2026-09-02 until today:

| Consumer | Broken call | Effect |
|---|---|---|
| `lib/cron/sip-auto-execute.ts` | `getSchemeCodeByIsin` | **no SIP executed since 2026-08-15** |
| `mutual-funds/refresh-navs` | `getByIsin` | MF valuations frozen; net worth understated |
| `mutual-funds/search` | `searchByName` | fund search returned nothing |
| `mutual-funds` (list/create) | `getByIsin`, `getBySchemeCode` | could not add a fund |
| `mf-redeem-worker`, `[id]/redeem` | `getSchemeCodeByIsin` | a redemption would stick PENDING forever |
| `agent/market-data`, `agent/watchlist/search` | `getByIsin`, `searchByName` | analyst MF signals blind |

Historical NAV (`getHistoricalNavOn`, `getNavHistory`) goes to mfapi.in, not the
AMFI file, and was unaffected — which is why the backfill can price each missed
installment at its true historical NAV.

### Why nobody noticed for three weeks

`runSipAutoExecute` pushes a fund it cannot price onto a `skipped[]` list and
returns **normally**. `cron/tick` only marks a job failed if it *throws*. So
`scheduled_jobs` recorded 90 consecutive `last_run_status = success` runs with
an empty `last_run_error`, while zero SIPs executed. The observability gap is
the more serious half of this bug.

### Fix

1. **`parseNavAll()` is now end-anchored.** NAV is `cols[len-2]`, date is
   `cols[len-1]`, identifiers are `cols[0..2]`, and everything between is joined
   into the display name. Correct for the 6- *and* 8-column layouts, and immune
   to AMFI inserting further descriptive columns in the middle. Rejected
   alternative: bumping the guard to `!== 8`, which breaks on the ninth column —
   same class of bug.
2. **`fetchAndCache()` no longer caches an empty parse.** A non-empty file that
   yields zero funds is a format break, not a quiet day: it logs loudly with the
   first offending data line and serves the stale cache instead of an empty NAV
   universe.
3. **`AMFI_ENDPOINT` pinned to `portal.amfiindia.com`.** `www.amfiindia.com` now
   302-redirects there. `fetch` follows it, so this was not itself breaking us —
   pinned so we do not depend on a redirect AMFI may retire.
4. **`cron/tick` reports non-throwing failure.** New `summariseOutcome()` folds a
   job's own `skipped`/`errors` payload into `last_run_error` even on success,
   prefixed `NOTHING EXECUTED —` when the job did nothing at all. A silent total
   outage is now visible in `scheduled_jobs` and in the container log.
5. **New canary `scripts/check-amfi-nav-feed.mjs`.** Asserts against the live
   feed that NAV is second-to-last, date is last, and ISIN sits in column 2 or 3
   — i.e. the assumptions the parser rests on. Deliberately does not
   re-implement the parser (a copy would drift). Exits non-zero on a break.

### Verification

- Fixed parser against today's live feed: **0 → 14,107 funds**.
- Legacy 6-column fixture still parses correctly (no regression if AMFI reverts).
- 12 of the 13 prod SIP ISINs resolve. The one that does not, `INF966L01A35`
  (demo SIP #77, Quant ELSS), is bad synthetic seed data — that ISIN does not
  exist at AMFI; the real one is `INF966L01986`. Pre-existing and demo-only,
  which is why that SIP has never executed since 2026-07-25. Not fixed here.
- Dry run of the backfill against prod state, then confirmed against the rows
  actually written after redeploy.

were priced at their own historical NAVs:

### Known, not fixed here

- SIP #74 is dated 2026-09-05 but 09-05 has no published NAV, so it prices at
  the 09-07 NAV while the transaction row keeps the 09-05 date.
  `sip-auto-execute` uses `getHistoricalNav` (value only); the redemption path

- There is no scheduled job that refreshes MF NAVs — `refresh-navs` is an
  on-demand route only, so between SIP executions the stored NAVs go stale.

## fix(sip): never price an installment from a stale AMFI NAV

**Area:** `src/lib/cron/sip-auto-execute.ts`

Found while auditing whether the backfill would pick the right NAV date. It
turned out there were **two** successive failures, not one — and the first was
worse, because it corrupted data instead of stopping.

| | Early August 2026 | Late August onward |
|---|---|---|
| Trigger | container DNS died | AMFI went 6 → 8 columns |
| `fetch` | **throws** | succeeds |
| AMFI cache | `catch` → returns **stale cache** | parses to **0 funds** |
| ISIN → scheme code | resolves (from stale cache) | null |
| Outcome | **SIPs executed at a frozen stale NAV** | SIPs skipped entirely |

Container DNS death is chronic on this host — `~/pfd-watchdog/watchdog.log`
opens with `2026-08-20 PROBLEM=container-dns-dead` and fired four more times on
2026-09-08. The watchdog was installed 2026-08-15, *after* the August incident,
so that window is uninstrumented; the failure it exists to catch is the one that
fits the data.

### The defect

`AmfiFund` carries `navDate`. Nothing looked at it:

```
fetchAndCache()       catch → return cache.funds        // stale, age not surfaced
getBySchemeCode()  →  AmfiFund { nav, navDate }          // navDate is RIGHT THERE
sip-auto-execute:160  fallbackNavRupees = currentFund.nav // navDate ignored
```

AMFI's file carries only the *latest* NAV, and on a fetch failure the service
hands back a stale copy with no indication of age. The executor accepted `.nav`
as the price for `nextDue` without asking what date it belonged to. A transient
DNS blip therefore became permanently wrong transaction prices instead of a
retry. The final fallback in the same expression, `?? lastNav / 100`, was worse
still — it would price a real purchase from the fund's own previously stored NAV.

### Fix

Apply the same on-or-after rule the mfapi path already uses: the AMFI fallback
is an acceptable price for `nextDue` only if `navDate >= nextDue`. Otherwise
**skip and retry** — the catch-up `while` loop means nothing is lost by waiting,
whereas a wrong price is written permanently and silently corrupts units, XIRR
and cost basis. The `lastNav` guess is removed entirely (the variable existed
only to feed it).

This had to ship alongside the AMFI parser fix, not after it: that commit added
"on a 0-fund parse, serve the stale cache", which is correct for scheme
*identity* (codes and ISINs never change) but widens the very path that produced
the bad prices. Stale identity is safe only once a stale NAV cannot become a
price.

### Verification

Replayed the real August conditions through the patched decision logic:

| Scenario | Before | After |
|---|---|---|
| Aug 05 due, AMFI frozen at 08-04 | executed @ ₹93.36 | **SKIP** |
| Aug 07 due, AMFI frozen at 08-04 | executed @ ₹62.25 | **SKIP** |
| Aug 10 due, AMFI frozen at 08-04 | executed @ ₹86.62 | **SKIP** |
| Aug 01 due, AMFI NAV from 07-31 (before due date) | executed @ ₹233.49 | **SKIP** |
| mfapi has the due date | execute | execute (unchanged) |
| Holiday — mfapi returns next published NAV | execute | execute (unchanged) |
| mfapi down, AMFI NAV current (`navDate >= due`) | execute | execute (unchanged) |
| AMFI unavailable entirely | error | error (unchanged) |

All four corruptions refuse; all four healthy paths, including the holiday
next-published-NAV rule, are untouched. Combined with the `cron/tick` outcome
reporting from the previous commit, these skips now surface in
`scheduled_jobs.last_run_error` as
`NOTHING EXECUTED — … refusing AMFI's 2026-08-04 NAV`.

### Existing bad data (NOT corrected — awaiting a decision)

Audited all 50 historical `SIP_EXECUTION` rows against mfapi's dated history.
Two rows on the personal account are **provably** mispriced:

| txn | date | NAV used | correct NAV | off by |
|---|---|---|---|---|
| 50 | 2026-08-01 | ₹233.49 (the **07-31** NAV — impossible via the correct path) | ₹236.539 (08-03) | 1.3% |
| 52 | 2026-08-07 | ₹62.25 | ₹63.6137 (08-07) | 2.1% |

The eight 2026-08-10 rows differ from their true date's NAV by only ~0.1%, which
is inside the ambiguity of value-based date attribution (08-04 and 08-10 NAVs are
very close for these funds). Not provable, so not claimed.

Aggregate: ₹36,000 of purchases, units overstated by 2.4542 (0.85%), ~₹250–300 of
overstated holdings value. 1.99 of those 2.45 units come from the two rows above.

Also confirmed correct and deliberately left alone: when a due date falls on a
weekend or exchange holiday, `getHistoricalNav` takes the next published NAV
(2026-05-10 Sun → 05-11; 2026-05-01 May Day → 05-04). That is the right
behaviour and matches how an AMC processes a non-business-day SIP.

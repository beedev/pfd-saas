# Changes — 2026-09-11

## prod data: August stale-NAV correction applied

**Area:** `vaspar-pfd` prod DB (`investment_transactions`, `mutual_funds`) — data
only, no code.

Corrected the two SIP installments that the early-August container-DNS outage
priced from AMFI's stale in-memory cache. RCA and the code fixes are in
`CHANGES-2026-09-09.md`; this is the data remediation.

| | before | after |
|---|---|---|
| txn 50 — HDFC Mid Cap, 2026-08-01 | ₹233.49 · 21.4144 units | **₹236.539 · 21.1382 units** |
| txn 52 — Motilal Flexi Cap, 2026-08-07 | ₹62.25 · 80.3166 units | **₹63.6137 · 78.5994 units** |
| `mutual_funds.id=8` units | 547.5790 | **547.3020** |
| `mutual_funds.id=4` units | 3110.7100 | **3108.9900** |

Why those two and not the other eight August rows: txn 50 used the **07-31** NAV
— a value from *before* its due date, which the on-or-after search can never
return — and txn 52's ₹62.25 is the **08-04** NAV (₹62.2536) rounded, on an
08-07 installment. Both are unambiguous. The eight 08-10 rows differ from their
true date's NAV by only ~0.1%, inside the ambiguity of matching a NAV by value
rather than by date, so they were left alone rather than rewritten on a hunch.

Method notes worth keeping:
- `amount` / `total_cost` untouched — ₹5,000 really was invested each time. Only
  the price and the units it bought were wrong.
- Units adjusted by **delta**. `mutual_funds.units` is NOT derivable from
  `investment_transactions`: funds 4 and 8 carry v1-import opening balances
  (2766.79 and 433.77 units) with no transaction rows, so `SUM(quantity)` would
  have destroyed most of the position.
- `nav` / `current_value` / `gain_loss` / `gain_loss_percent` / `expected_xirr`
  deliberately left stale — all derived, and the SIP backfill recomputes them
  from the corrected base. Hence the ordering: correct the data, **then** deploy.
- Each `UPDATE` is gated on the old `price_per_unit`, so a re-run matches zero
  rows. Verified after commit.
- Both rows carry an audit note recording the old value and why it was wrong.

Ran as a single `BEGIN … COMMIT` after a dry run of the identical script ending
in `ROLLBACK`. Rollback points that already existed were used rather than
creating new ones (see the backup note added to CLAUDE.md).

  `docker run`, `deploy-prod.sh` and prod-DB writes are all blocked, so the
  human runs the deploy. Documented so future sessions hand over the command
  instead of retrying.
- **Documented deploying from a git worktree**, since the clean-tree gate usually
  rules out `~/Desktop/pfd-saas`.
- **Backups:** three layers already run on a schedule (entrypoint
  `pre-migrate-*.dump` on every start keeping 7, `deploy-prod.sh` →
  `~/pfd-backups/`, monthly LaunchAgent on the 1st at 03:00). Do not add ad-hoc

  not. `feat/desktop-analyst` — usually the checked-out branch — has **diverged**

- **New invariants** from the 09-09 incident: parse third-party feeds

- **Docs index added** pointing at `docs/ARCHITECTURE.md` (arc42),
  `docs/backup-restore.md`, `docs/portability.md`,
  `docs/DESKTOP-ARTHA-HANDOFF.md`, `docs/PLAN-telegram-assistant.md` and the

## docs: operations runbook — capture the operational knowledge lost between sessions

**Area:** `docs/OPERATIONS-RUNBOOK.md` (new), `CLAUDE.md`, agent memory

Bharath's observation, and the reason this exists: roughly half this session went
on rediscovering things that were already true and already written down
*somewhere* — just not in one place. Specifically the struggle was with (a)
deploying to Docker, (b) running queries against the containerised Postgres, (c)
finding where backups live, and (d) generally reconstructing how the running
application is wired, which earlier sessions knew and a fresh session did not.

New `docs/OPERATIONS-RUNBOOK.md`, eight sections:

1. **What is actually running** — V1 (sunset) vs pfd-saas dev vs vaspar-pfd prod,
   and that ONE prod container runs four things: Postgres (bound to 127.0.0.1,
   **not published**), Next standalone, a 60 s cron ticker and a 5 s Telegram
   ticker. Plus the `/data/.secrets` inventory, so nobody passes `-e` secrets again.
2. **Querying the prod DB** — the canonical `docker exec … psql` line; role and DB
   are both `pfd_saas` (not `postgres`, not `pfd`); **always write SQL to a file
   and `docker cp` it** rather than fighting three levels of shell quoting; dry-run
   writes ending in `ROLLBACK;`; guard `UPDATE`s on the old value. Records the
   specific traps hit today: `''x''` collapsing to bare `x`, a `Q`-substitution
   hack corrupting unrelated text, a long one-liner wrapping on paste and splitting
   `-U` from its argument, `next_execution_date` being `text` not `date`, and a
   mid-script `psql` error making the *next* statement's empty output look like an
   empty table (which is how the stuck Telegram row was missed on the first pass).
   Includes the `information_schema` sweep that finds a value when you don't know
   which table holds it.
3. **Deploying** — `scripts/deploy-prod.sh` is the only sanctioned path, with the
   five things a hand-rolled `docker build && docker rm -f && docker run` skips
   (clean-tree gate from the 2026-06-21 untracked-migration incident, pre-deploy
   backup, `git.sha` labels, `-e APP_OWNER=Bharath`, health wait). The three branch
   lineages and why prod must come from `feat/analyst-agent`. How to deploy from a
   worktree. How to verify what actually shipped, and to use `git grep` rather than
   `git show | grep` for branch checks.
4. **Backups** — the three layers that already exist (entrypoint `pre-migrate-*`
   on every start keeping 7; `deploy-prod.sh` → `~/pfd-backups/`; monthly
   LaunchAgent on the 1st at 03:00) and the instruction **not** to create ad-hoc
   dumps, which Bharath gave directly after I made a redundant one.
5. **Reading logs without being misled** — `docker logs` is cumulative across
   restarts and the app only logs on error, so the tail is whatever last broke,
   possibly weeks ago, and reads as current. Today's final entry was 22 days stale.
   Silence is not health.
6. **The cron system** — `scheduled_jobs` is per (user, job_type), so two of each
   `agent_*` row is correct not duplicated; a restart does NOT make a 24 h job run;
   the IST-anchored jobs; and how to trigger work now (the "Auto-execute all"
   button, the tick endpoint, or nudging `next_run_at`).
7. **Known operational hazards** — biweekly container-DNS death and the watchdog,
   the Telegram permanent-failure retry loop (still open), the deliberately
   out-of-step migration journal, and that `mutual_funds.units` is not derivable
   from `investment_transactions`.
8. **What the agent can and cannot do** — prod container teardown is always
   refused; prod DB writes are refused until explicitly approved in conversation;
   build/cp/exec/logs are allowed. Recorded so a future session hands over a short
   `!` command instead of burning turns retrying.

Also written to agent memory so a cold session loads the pointers rather than
rediscovering them: `project_prod_ops_runbook.md`,
`feedback_verify_with_the_right_tool.md`, `project_amfi_feed_stale_price.md`, with

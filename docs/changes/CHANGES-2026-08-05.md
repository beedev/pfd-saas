# Changes — 2026-08-05

## Fix: Budget Tracker blank for Aug 2026+ (cross-year window bug)

**Area:** `src/app/api/finance/budget/route.ts` (budget grid GET)

**Symptom:** The multi-month Budget Tracker showed every cell as "-" for
Aug 2026 and beyond; data was visible only through July 2026. Newly-added
entries for Aug+ also failed to appear even though they were written to the DB.

**Root cause:** The GET handler filtered `budget_entries` (and the
`credit_card_expenses` status query) by period using **string comparison**
on the MMYYYY format — `gte(period, from)` + `lte(period, to)`. MMYYYY is not
lexicographically orderable across a year boundary (as text `'122026' > '012027'`),
so any window spanning Dec→Jan produced an inverted, empty range and returned
zero rows. The default grid view is *current month + 5*, so every window from
Aug onward straddles the boundary → whole grid blank. Data was present but hidden.

**Fix:** Enumerate the exact MMYYYY periods in the requested `[from, to]`
window by stepping month-by-month with a numeric `(year*100 + month)` key
(logic already existed lower in the handler for status computation — lifted it
above the queries), then match with `inArray(period, periodsInRange)` instead
of a string range. Applied to both the entries query and the credit-card status
query. Removed the now-duplicate period-enumeration block. No schema change,
no data migration — existing rows were already correct.

**Not affected:** `budget/monthly/route.ts` queries a single exact period and
its recurring-window check already uses numeric YYYYMM — left unchanged.

**Verification:**
- ESLint + `tsc --noEmit` clean.
- Postgres proof: `'082026' <= '012027'` → false; old string range over the
  Aug2026–Jan2027 window returned 0 rows while 48 entries existed in 2026.
- Prod data proof (`personal@pfd-saas.local`): OLD string range → 0 rows;
  NEW `inArray` window → 14 rows (the hidden Aug 2026 + Father Sept entries).

**Deploy:** Rebuilt `vaspar-pfd:latest` and redeployed the production container
(volume `vaspar-pfd-data` preserved). Pre-deploy backup:
`~/pfd-backups/vaspar-pfd-pre-budgetfix-05082026.dump` (5.6 MB). No remote push.

## Data fix: Amazon Aug 2026 budget line stuck at 0 (prod)

**Area:** prod DB (`vaspar-pfd`) — `budget_entries`, `personal` account

**Symptom:** In the Budget Tracker, the Amazon card row for Aug 2026 showed
blank / not-paid, even though the Amazon statement was fully paid.

**Root cause:** Amazon's Aug `credit_card_expenses` row is fully paid
(amount = paid = ₹1,15,185, paid 03-Aug), but its matching `budget_entries`
row was 0/0 — the card→budget sync never populated it during the bulk personal
data load (05-Aug 02:2x), while Tata Neu and Axis Select synced correctly. The
grid renders the budget-entry amount, so Amazon showed blank. Live app paths are
fine (`mark-statement-paid` and add-expense both call
`recomputeCreditCardBudgetForPeriod`); this was a one-off import gap. Reconcile
across all cards × months confirmed Amazon-Aug was the only fully-paid-but-zero
row (two May rows differ by a few rupees — benign manual rounding, left as-is).

**Fix:** One guarded UPDATE setting Amazon/082026/personal
`planned_amount = actual_amount = 11518500` (the ledger's paid amount — exactly
what the sync would have written). Reversible; pre-fix value 0/0.
Backup: `~/pfd-backups/vaspar-pfd-pre-budgetfix-05082026.dump`.

# Changes — 2026-09-18

## fix(tax): 44ADA presumptive income ignored — gross receipts taxed as profit

**Reported:** the Income Tax page for FY 2026-27 showed Business / professional
₹27,18,310 and a balance to pay of ₹1,16,082, with no 44ADA treatment.

### Root cause

`src/lib/finance/tax-compute.ts` — presumptive treatment applied only when a
`presumptive_income` row existed for that **exact** FY:

```ts
const businessPaisa = presumptiveRows.length > 0 ? presumptiveDeclaredPaisa : gstReceiptsPaisa;
```

Prod had one presumptive row, for FY **2025-26** (44ADA, receipts ₹33,24,922,
declared ₹16,62,461 — exactly 50%, correct). FY 2026-27 had none, so the ternary
fell through and taxed the FY's GST receipts in full: 6 invoices, ₹27,18,310,
matching the on-screen figure to the rupee.

Running FY 2026-27 NEW slabs over business income alone:

| basis | slab-able | tax + 4% cess |
|---|---|---|
| receipts taxed as profit (what happened) | ₹27,18,310 | ~₹4,11,313 |
| 44ADA 50% deemed profit | ₹13,59,155 | ~₹87,228 |

**~₹3.2L of overstated tax.** (Standalone slab model; it does not reproduce the
capital-gains interaction, so treat the delta as the finding, not the absolutes.)

### The defect was the silence, not the fallback

The missing row is data — presumptive is a per-year election and cannot be
inferred from a prior year (eligibility limits, and a five-year lock-out on
opting out of 44AD). Auto-applying 50% was considered and **rejected**: that is
the same silent-wrongness in the opposite direction.

The bug is that the fallback said nothing. Gross receipts are not a profit figure
under *any* regime — a presumptive filer is taxed on 50% or 6-8%, a regular filer
deducts expenses — yet the page rendered a bare "Business / professional
₹27,18,310" indistinguishable from real profit. Same shape as the AMFI NAV
incident: a plausible-looking number, wrong by ~2×, with no signal.

### Fix

- `tax-compute.ts` tags the basis (`PRESUMPTIVE` / `GROSS_RECEIPTS` / `NONE`),
  returns a `businessDetail` string and a new top-level `warnings[]`. When the
  fallback fires the warning names the receipts, the 44ADA figure, and the fact
  that no declaration exists for the FY. Math unchanged — purely additive.
- `/api/tax/regime-compare` passes `warnings` through.
- `RegimeComparisonCard` renders warnings **above** the numbers, and labels the
  line `· GROSS RECEIPTS, not profit` (amber) or `· presumptive profit` (green).

Verified against real prod data for all three paths: FY 2025-26 → PRESUMPTIVE,
₹16,62,461, no warning (unchanged); FY 2026-27 → GROSS_RECEIPTS + warning naming
₹13,59,155; an FY with no receipts → NONE, silent.

## feat(tax): presumptive income is now a first-class destination

Raised while fixing the above: *"Where can I declare presumptive taxation? It
cannot be in ITR Wizard."*

It effectively could not be reached. The only UI was
`/tax/itr4/presumptive/new`, reachable only from `/tax/itr4`, reachable only from
the ITR wizard's "Continue to ITR-4 walkthrough" button — i.e. only once the
wizard had already recommended ITR-4. The sidebar had **no** ITR-form links at
all. (`docs/SPRINT-HISTORY.md:504` claims Sprint 4.1 added explicit ITR-1/2/3/4
sidebar entries; it did not — another stale claim.)

That layout is also circular: the wizard picks your form from your income
composition, but whether you file presumptively *is* part of that composition. You
were asked to accept a form recommendation before being allowed to state the fact
the recommendation depends on.

**Presumptive income is an income declaration, not an ITR-form artifact** — it
sets taxable business profit for every form and both regimes, and feeds
regime-compare, advance tax and the ITR selector. So:

- Moved `(dashboard)/tax/itr4/presumptive/*` → `(dashboard)/tax/presumptive/*`
  and `api/tax/itr4/presumptive/*` → `api/tax/presumptive/*` (`git mv`, so history
  follows). Old UI paths kept as **redirects** so bookmarks don't 404.
- New standalone `/tax/presumptive` list page: declarations for the FY, a
  compliance column checking each row against its statutory minimum (50% for
  44ADA, 6%/8% for 44AD by receipt mode, manual for 44AE, flagging 44AB(e) audit
  exposure), a section-explainer card, and — the point — **the FY's GST receipts
  shown next to the declaration**, so a missing or wrong one is obvious.
- **Sidebar**: "Presumptive Income" under Income Tax, above the ITR tooling.
- **`/income`**: a link under the Freelance / Business (GST) row, relabelled to
  say those are *receipts*, and that presumptive is what turns them into profit.
- `/tax/itr4` keeps its card and now reads the rows rather than owning them.

Entry points went from effectively zero to five.

## fix(gst): Settings fabricated an invoice prefix you never set

**Reported:** Settings shows `INV-` but sales invoices are `0007/26-27`.

The DB was right and the form was lying. `business_profile.invoice_prefix` is
empty (verified, length 0), which is exactly what selects the FY-suffixed format
in `/api/gst/invoices/next-number`:

```ts
const nextInvoiceNumber = prefix ? `${prefix}${paddedNum}` : `${paddedNum}/${fySuffix}`;
```

But `business-profile-form.tsx` loaded it as `data.profile.invoicePrefix || 'INV-'`.
`'' || 'INV-'` is `'INV-'`, so an empty stored prefix **rendered** as `INV-`.

This was armed, not cosmetic. Opening Settings for any unrelated reason and
saving would have **persisted** the phantom `INV-`, turning the next invoice into
`INV-0008` instead of `0008/26-27` and breaking a GST invoice series mid-year —
a compliance problem, since a series is meant to be continuous for the FY.

`||` cannot distinguish "not set" from "deliberately empty". For a field where
empty is a meaningful choice it is the wrong operator.

- Load with `?? ''`; form default `''` rather than `'INV-'`.
- The field description is now live and shows the consequence before you save:
  filled → "Next invoice will look like INV-0008"; empty → "Leave empty for the
  financial-year format — next invoice will look like 0008/26-27".

The API already stores `invoicePrefix || null`, which is correct — null and empty
both select the FY format.

## chore: SCHEMA_HASH was stale in git

`src/lib/portability/schema-hash.generated.ts` regenerated during this build.
`src/db/schema.ts` was **not** touched in this session — the committed hash was
simply out of date:

| | sha256 |
|---|---|
| true hash of `src/db/schema.ts` | `b83ccc7b…` |
| committed in git | `b37c9d27…` (stale) |

A prior schema change was committed without a production build, so the `prebuild`
hook never refreshed it. It matters because that hash is the version gate for the
portability export/import flow, and `prebuild` does **not** run under
`npm run dev` — so dev was using a fingerprint that matched no schema, and an
export made in dev would have been refused by a built container (and vice versa).
The regenerated value is correct. Worth a guard in CI eventually: fail if
`compute-schema-hash.mjs` produces a diff.

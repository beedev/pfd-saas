## Fix: scheduled-job times showed +5:30 off (PGlite local-TZ vs Postgres UTC)

RCA: the app stores time in naive `timestamp` columns and assumes UTC (the
Docker/Postgres convention). PGlite on the Mac defaulted its session to local IST,
so `NOW()` stored IST wall-clock; the jobs-status query then did
`AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Kolkata'`, adding a second +5:30. Evidence:
daily_digest last_run stored '09:31' (IST wall-clock at a 09:41-IST backup), shown
as 15:01.

Fix (Option A — normalize the environment, so one codebase stays correct on both
PGlite and Postgres):
- `electron/main.js`: added `TZ: 'UTC'` to the Next-server child env — the whole
  server now runs in UTC exactly like the old container.
- `src/db/index.ts`: belt-and-suspenders `SET TIME ZONE 'UTC'` on the PGlite session
  at init (idempotent, queues before any request query).

One-time re-baseline of Bharath's existing (IST-polluted) `scheduled_jobs` via a
throwaway script (`timezone('UTC', timezone('Asia/Kolkata', ts))`) so recurring jobs
didn't stall ~5h in the new UTC frame. pgdata snapshotted to `pgdata.bak-tzfix`
first. Fresh installs import UTC prod data and never need this — the re-baseline was
NOT shipped.

Verified: after rebuild+install, alerts_check now stores last_run '2026-08-18
06:12 UTC' (was IST) and next_run 06:17 UTC (recurring, not stalled); jobs page
+5:30 → 11:42 IST = correct current time. Analyst jobs confirmed running (agent_runs
has today's daily+intraday). Known follow-on (deferred, pre-existing TODO): the full
`timestamp`→`timestamptz` migration (~80 cols) and early-morning jobs missing when
the Mac sleeps.

## Hardening: clear stale postmaster.pid on startup (crash-safe always-on)

During the TZ fix, repeated hard-kills left a stale `pgdata/postmaster.pid`, which
brought PGlite up READ-ONLY on the next start — every UPDATE failed with "cannot
execute UPDATE in a read-only transaction", poisoning the single PGlite connection
(cascade of "current transaction is aborted") and taking health to db:down. Data was
never at risk (backups dumped fine throughout); a clean restart after removing the
stale pid restored write access.

Because always-on restarts Artha after a crash (KeepAlive), this could recur on any
unclean shutdown (crash / force-kill / power loss). Fix in `electron/main.js` boot():
before opening PGlite, if `pgdata/postmaster.pid` exists and the PID it names is not
running (`process.kill(pid, 0)` throws), remove it; if the PID IS alive, leave it.

Verified: planted a stale postmaster.pid (pid 999999) → launcher logged "cleared
stale postmaster.pid (pid 999999 not running)" and came up healthy (db:up). Also
re-confirmed on this build: alerts_check stores last_run in UTC (06:17), Dock shows a
single icon (next-server = UIElement), always-on running.

## Fix: installer failed on another Mac (bash-isms under zsh)

RCA: `Install Artha.command` was bash-syntax but ran under zsh (macOS default shell).
`read -r -p` errors in zsh (`-p` = read-from-coprocess, not prompt), and when the
file's exec bit was stripped in transfer the shebang wasn't honored so comments/`[[ ]]`
ran as commands and `$0` was `-zsh` (→ `dirname` failed → "Artha.app not found").

Fix: rewrote the installer in portable POSIX sh (`#!/bin/sh`, `printf`+`read -r`,
`case` instead of `[[ =~ ]]`, `set -eu`, ASCII glyphs). Verified: `sh -n`/`bash -n`/
`zsh -n` all pass; full dry-run under zsh (redirected to /tmp) completes and generates
a valid plist. README gained a foolproof fallback ("type `sh ` then drag the file into
Terminal") for the exec-bit-stripped case, and now leads with drag-to-Applications as
the most reliable path. .dmg rebuilt.

NOTE / self-inflicted incident: while dry-run testing, a careless sed left a bare
`cp ... /Applications/` unredirected and overwrote the real /Applications/Artha.app
binary with a 10-byte stub → app went db:down. Restored the binary from the dmg;
the stale-postmaster.pid hardening auto-cleared the crash lock on restart (validated
in production: "cleared stale postmaster.pid (pid -42 not running)", health db:up).
Lesson: never run installer scripts with real-path side effects during testing.

## Fix: app "installs but won't open" on another Mac (dangling symlinks + no signature)

RCA (two bugs, both in packaging, not the installer):
1. `.next/standalone/.next/node_modules/` held symlinks pointing to ABSOLUTE
   build-machine paths (`/Users/bharath/.../node_modules/@electric-sql/pglite`
   etc.). On any other Mac these DANGLE → the Next server can't load its external
   packages (pglite/pdfjs/react-pdf) → it never starts → the window never opens.
2. `identity: null` made electron-builder skip signing entirely → the bundle had
   no `_CodeSignature` seal (`codesign --verify`: "code has no resources but
   signature indicates they must be present"). Runs on the build Mac (not
   quarantined) but Gatekeeper rejects it on any other Mac.

Fix in `electron/after-pack.js` (runs after the standalone copy, before dmg):
- Walk the copied tree; every symlink whose realpath escapes the bundle is
  re-pointed as a RELATIVE in-bundle link to the same package under
  `dst/node_modules` (no copy, no bloat, portable). Removed with `unlinkSync`
  (fs.rmSync follows a symlink-to-dir and throws "Path is a directory").
- Then ad-hoc sign the complete bundle: `codesign --force --deep --sign -` +
  `--verify --deep --strict` as a build-time guard.

Verified: build logs "4 symlinks re-pointed in-bundle" + "ad-hoc signed + verified
bundle"; 0 escaping symlinks; `codesign --verify --deep --strict` PASS; re-pointed
pglite resolves in-bundle; installed the build → health db:up (re-pointed pglite
loads at runtime). .dmg 316M (15:20). Combined with the installer's quarantine
removal, the app now launches on any Apple-Silicon Mac. (arm64-only still — an Intel
Mac cannot run it regardless.)

## Fix: TZ regression (JS displays 5:30 behind) + install must use ditto

Two issues surfaced late in the desktop work:

1. TZ regression. The earlier timezone fix used TWO levers: `SET TIME ZONE 'UTC'`
   on the DB (correct — fixes storage + the jobs page) AND `TZ=UTC` on the whole
   process (wrong — it made server-side JavaScript format dates in UTC, so any
   display not explicitly bound to Asia/Kolkata showed 5:30 behind). Fix: removed
   `TZ=UTC` from the Electron child env in main.js; kept the DB `SET TIME ZONE`.
   Verified in a scratch PGlite that `SET TIME ZONE 'UTC'` keeps NOW() stored as
   UTC even with the host process in IST — so the jobs page stays correct while JS
   returns to IST. Confirmed on the running app: alerts_check stores 10:13 UTC →
   page shows 15:43 IST (correct); jobs-status query proven correct on restored
   data (raw 09:55 UTC → displays 15:25 IST).

2. Install must use ditto, not cp -R. cp -R breaks a bundle's code-signature seal
   ("a sealed resource is missing or invalid"), so on Apple Silicon the app can be
   killed at launch with no output (crash-loop, exit 1). ditto preserves the seal.
   The shipped installer already uses ditto (Bharath's improvement, now merged);
   my manual cp -R test-installs were what broke it. Reinstalled via ditto →
   signature valid (exit 0), app boots healthy.

Also merged Bharath's improved installer into the shipped one: POSIX sh (zsh-safe),
auto-find Artha.app on /Volumes, admin-privilege ditto copy when /Applications is
protected, quarantine removal, offer-to-open, PLUS the always-on opt-in. .dmg
rebuilt + ad-hoc signed with in-bundle symlinks (portable to other Macs).

import would wipe it sooner. No DB surgery performed.

# Changes — 2026-08-15

## Host-side watchdog for the recurring Docker VM wedge

**Context:** the Docker Desktop VM has wedged twice in two weeks (2026-07-31
read-only remount; 2026-08-14 DNS-forwarder death) — each time the running
container keeps serving but loses outbound DNS, silencing Telegram and freezing
the overview, and only a Docker Desktop restart clears it. A restart is a cure,
not a prevention, and Bharath was the one discovering the wedge both times.

**What was added (host infra — lives OUTSIDE the repo):**
- `~/pfd-watchdog/watchdog.sh` — every 5 min, bounded-checks (1) daemon
  responsive (`docker version`), (2) container DNS resolves `api.telegram.org`,
  (3) `/api/health` 200. Classifies `daemon-wedge` / `container-dns-dead` /
  `app-down`.
- `~/pfd-watchdog/watchdog.env` (chmod 600) — Telegram bot token (captured once
  from the container's `/data/.secrets`) + chat_id 8561741967.
- `~/Library/LaunchAgents/com.bharath.vaspar-pfd-watchdog.plist` — RunAtLoad +
  StartInterval 300, logs under `~/pfd-watchdog/` (NOT ~/Desktop — avoids the
  LaunchAgent exit-78 TCC trap).

**Recovery policy (Bharath chose "full auto-restart"):**
- `daemon-wedge` / `container-dns-dead` → restart Docker Desktop (quit →
  SIGKILL survivors, leaving root `vmnetd` → `open -a Docker` → poll daemon up).
  **This bounces the kgi stack too** (kgi-valkey/postgres/kong) — accepted.
- `app-down` (daemon fine) → lighter `docker restart vaspar-pfd`, kgi untouched.
- Anti-flap: acts only after **2 consecutive** failed runs, and at most once per
  **15 min** (cooldown). Telegram alert before + after every action.

**Verified:** Telegram test delivered ("to: Bharath"); watchdog run on the
healthy system is a clean no-op (state `0 0`, no restart, no log spam);
LaunchAgent `LastExitStatus 0`, launchd stderr empty; enabled at login.

**Still open / not done:** root-causing *why* the Docker Desktop VM wedges
(a Docker Desktop / macOS-level issue) — the watchdog treats the symptom fast
but doesn't prevent the wedge.
